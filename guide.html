Build, simulate and install a TinyDesk app

Create simple interfaces with ready-made elements, or attach MicroPython handlers for advanced behavior. Keep the editable JSON and your exported package together with the app version.

1. Open the builder

Start the local helper from the App Builder folder:

python tools/studio_simulator.py
# Open http://127.0.0.1:8773/

The helper needs a matching native mpy-cross compiler and TinyDesk tdsim runtime. Supply --compiler PATH and --runtime PATH if they are not found automatically. The helper listens on your computer only. Opening index.html directly supports editing and Python export; compiled packages and real simulation use the helper.

2. Choose the screen and add pages

  1. Choose the board’s actual screen size. CrowPanel font 20 uses 80 × 24 cells. Select the PSRAM target for rich image-based interfaces.
  2. Add a window and choose fullscreen for a kiosk. Add pages with the + beside the page tabs. Set the window’s normal startup page in its Inspector.
  3. Add elements from the component gallery: text, buttons, rectangles, gradients, gauges, progress bars, sliders, images, checkboxes, lists and text inputs.
  4. Select an element on the canvas or in the Outline. Its attributes appear in the fixed right Inspector. Drag to move; drag handles to resize. Arrow keys move by one cell, Shift by five. Ctrl+Z undoes.

Cell coordinates follow the terminal grid. Pixel drawing coordinates use two logical pixels per cell; pictures and image buttons render at the display’s native resolution. The Inspector states the units. Leave room between values and controls, and test readability on the actual LCD.

3. Style elements and import artwork

Use the Palette button beside a color field. It shows the device’s 256 colors; a custom RGB color selects the nearest supported color. Theme default inherits the desktop. Transparent is available only where supported.

For rectangles and geometric buttons choose Straight corners or Rounded corners, then adjust radius. Changes redraw immediately. The outline setting controls filled versus outlined shapes. Buttons have separate normal, pressed, rim and text colors. A skinned button shows Image skin corners. Choosing Straight or Rounded replaces its sprite sheet with its geometric colors; enabling the optional sprite sheet restores the default skin. Device pixel resolution limits rounding on very small shapes. Later overlapping elements, including opaque labels, can cover the corners; inspect their backgrounds and drawing order.

Import image / text embeds the resource in your project. PNG, JPEG, WebP and BMP imports are converted to a device image; large images are reduced to 256 pixels on the longest edge. Binary P6 PPM and P5 PGM imports preserve dimensions up to 512 × 512. Transparent source pixels use a color key. Resize the image element without editing the source. The package includes its resources automatically. Text-file import creates editable label lines.

Assets in the left pane

Choose Assets beside Components and Outline. Every imported or referenced image, text source and module is listed, including external files. Search by name and select a file to see its preview, dimensions, stored size and element references in the fixed Inspector. Click a reference to select that exact element and page. Use Locate/Replace to repair or change a file, Download to save an embedded copy, or Remove unused for a file with no references. Removal supports Undo.

Enabling the default sprite sheet embeds the shared button skin automatically and preserves a custom skin already using that filename. Text imports retain their source file and create independently editable labels; replacing the source does not rewrite those labels. Portable .mpy imports are retained and declared as application dependencies; keep their Python source separately.

4. Add behavior without a separate GUI implementation

Name fields so events can update them. A button offers press, release, click and cancel callbacks, with starter actions such as switching pages or changing text. A slider can bind to another named value field. Edit the generated starter body for custom logic.

# Named value or label field
temperature.set(text="350 C")
# Named progress/gauge field
power.set(value=65)
# Change a page
show_page("Settings")

Use window timers for periodic work. The first custom page is assembled in one frame. Initialization callbacks run after that frame; first-window construction has a five-second ceiling, while ordinary drawing batches have a one-second ceiling. Keep callbacks short and return promptly; an infinite loop or blocking serial read freezes the app. For advanced device logic use application modules declared in Export options. Start the helper with --project-dir PATH to a private module/asset folder. Importing a .tdapp preserves compiled dependencies even if the original sources are not installed.

5. Choose the startup screen

  1. Add a custom page, for example Welcome. Place your imported logo on that page and set its background.
  2. Open Startup screen. Choose Standard status screen (default), or Custom page.
  3. Select the entry page. A positive Show for delay opens the window’s normal startup page afterward. Set 0 to stay on the entry page until your events navigate away.
  4. Choose imported artwork for the kiosk loading stage. Place that artwork on the custom page too for a continuous transition.

Custom entry pages work in simulation and on the board. Replacing the kiosk’s early status message also requires the generated installation settings below and firmware supporting kiosk.splash/kiosk.status. Until the display is initialized, firmware boot diagnostics may still appear on a serial console.

6. Simulate before exporting

The current preview composes native cell frames and image data into one display, keeping backgrounds and large values independent of browser text rendering. Update/rebuild tdsim when updating the helper: it must support cells=FILE. Restart the helper and reload App Builder after an update.

Press Run simulation. This runs the generated Python in TinyDesk with MicroPython, including real page, mouse, slider, button and timer behavior. Press Stop and edit to return. Each new run starts with fresh app state. Another tab starting a simulation replaces the previous session.

If an image is missing, open Resources to see its exact filename and choose Locate image. Select the local file; the existing elements keep their geometry and use the embedded resource. Import image / text also repairs an existing image when its filename matches a required reference, rather than adding a duplicate element. Replace image updates all elements sharing that file. Save JSON afterward so it travels with the project. Package imports recover images and bytecode automatically; bare extracted project.json files contain resource metadata and need their files located again.

A status message explains startup failures; a black display is not a successful simulation. If the helper is unavailable, start it and use its URL. After updating App Builder or its helper, reload the editor. If a handler blocks, stop, remove the blocking operation and run again. The simulator cannot validate UART wiring, physical touch calibration, device performance or machine communication. Verify those on hardware separately.

7. Export one app file

  1. Fix red Design checks errors. Review overlap warnings. Save JSON as your editable source.
  2. In Export options set the application version, for example 1.2.0. The project tracks the builder version separately.
  3. Press Export app to download a single .tdapp containing project JSON, compiled MicroPython, images and module dependencies. Export Python/.mpy remain available for development.
  4. Press Install / kiosk for the exact settings for this export. Re-export and update these settings whenever the app changes.

8. Copy to the card or board and test

  1. Back up your existing app and /etc/board.conf. Check free storage. A .tdapp needs room for itself plus its extracted revision cache; budget approximately twice its size and space for logs.
  2. Use Board files with the board FTP helper to upload the .tdapp to /root. With a removable filesystem mounted by TinyDesk, copy it there and use its actual mounted path instead. On CrowPanel the default /root is internal flash: copying to a PC-visible SD card alone does not install there.
  3. Run the package once from the TinyDesk shell:
py /root/my_app.tdapp

The loader verifies file hashes and extracts a revision-specific .tdapp-… cache. Valid cached files are checked and reused on later launches, reducing flash writes; damaged files are restored from the package. Confirm pages, buttons, values and graphics. Keep your previous package for rollback. Do not enable kiosk while the app is failing.

Board files: exact upload steps

  1. Connect the board and computer to the same trusted network. On TinyDesk, sign in as root, configure Wi-Fi in Network, and note the board IP address.
  2. Start the board FTP server with ftp start. The root factory password must already have been changed on the board.
  3. In a second computer terminal, from the App Builder folder, run python tools/studio_bridge.py. Keep this helper and the simulator helper running. Copy the token it prints.
  4. Open Board files. Enter helper port 8765 and the printed token, then the board IP, FTP port 21, username and password. Click Connect. Credentials remain in session memory. FTP is unencrypted; use a trusted network.
  5. Open /root. Choose Design format → .tdapp (all resources), then Upload the current design. Or use Upload files to select an already exported .tdapp.
  6. Wait for the transfer’s final OK, including the board file-size check. Reconnect if the idle session has expired. Run the uploaded app from the board shell as shown above.

9. Register kiosk mode

  1. Close the test app. Open TinyDesk’s Files app, browse to etc/board.conf under the filesystem root, and open it in Editor.
  2. Copy the Install / kiosk settings into the file, replacing the existing values for those keys. Preserve other board, console, UART and network settings.
  3. Save with Ctrl+S, then run reboot in the shell. The kiosk starts the package automatically and restarts it after exit.
# Standard status screen example
kiosk.app = /root/my_app.tdapp
kiosk.status = 1
kiosk.splash =

# Custom artwork: use the EXACT cache path from Install / kiosk
kiosk.status = 0
kiosk.splash = /root/.tdapp-REVISION/logo.ppm

Run the exact package once before enabling its splash path. Re-exporting produces a different cache revision. Keep the current revision cache while it is referenced by kiosk.splash. A missing image with status disabled produces a black loading background.

10. Recovery, updates and long-lived apps

To leave kiosk temporarily, press F10 three times within two seconds or hold the top-right corner for five seconds, then enter the root password. On supported ESP32 boards, release RESET, then hold BOOT briefly within the first 1.5 seconds to enter maintenance mode with console access (holding BOOT through reset selects the ROM download mode). To disable kiosk permanently, remove or blank kiosk.app in board.conf and reboot. To roll back, restore the prior package and its matching kiosk settings.

Keep JSON, custom source modules, the .tdapp, app version and tested firmware version in version control or a project archive. App Builder releases do not rewrite installed apps. The package declares project schema, runtime API and MicroPython ABI requirements. Current packages use schema 1, TDAPP 1 and portable MicroPython v6.3 bytecode. Firmware must provide the APIs used by the app; test before upgrading firmware. Import old JSON, Python with embedded design, or .tdapp to edit it. Manual changes outside embedded design comments are not reconstructed as visual elements.

Old extracted caches can be removed after backing up and verifying the replacement. Never remove the active app’s cache. For continuous previews use bounded logs and timers; sample memory after warming up several page cycles. Keep private applications and branding outside public App Builder and TinyDesk repositories.

Text import, pixel sizes and generated fonts

  1. Click Fonts. Choose a system family, or import a .ttf / .otf file. Set the desired size in LCD pixels (8–96), select smooth 4-bit or compact 1-bit glyphs, and include every character your app may display. Generate preview, choose a unique filename and add the font to the project.
  2. Click Add text to type/paste text, or Import image / text to open a UTF-8 .txt file. Choose the generated font, alignment and wrapping, then add the editable text box. The original text file remains in Assets.
  3. Select the text box in the canvas or Outline. In the fixed Inspector, choose another font/size, change text and colors, and set horizontal/vertical alignment or wrapping. Drag the box to move it or use its handles to resize it. Increase its height when larger text needs more lines. Existing terminal/pixel text can be converted by choosing a generated font; buttons and image labels also accept these fonts.
  4. Check Assets for font preview, line height, glyph count, bytes and element references. Download a .tdfont to reuse it in another project. Save JSON, then Run simulation and Export app. Both JSON and .tdapp carry the generated glyphs; the board and future editor versions do not need the original desktop font.

Generated fonts require firmware with tdui.Font and Canvas.font_text. Fonts are loaded once and rendered in native C. Pixel sizes refer to actual device pixels: CrowPanel font 20 uses 10×20 pixels per cell, while font 16 uses 8×16. Native terminal labels keep their terminal-selected font. A generated font supports up to 512 glyphs and 256 KiB; each text element supports up to 900 UTF-8 bytes. Missing glyphs use ?. Keep the source TTF/OTF to generate more sizes. Complex-script shaping and Nextion .zi files are not supported.

Try examples/generated_fonts.json for a portable two-page project and examples/demo_text.txt for text import. Replacing an imported source file does not overwrite text you have edited in the canvas.

Group selection and shared attributes

Shift/Ctrl-click elements in the canvas or Outline to select several. Drag an empty area for a marquee, or focus the canvas and press Ctrl+A. The fixed right Inspector shows common fields; a blank or Mixed field means the selected values differ. Editing that field applies it to every element immediately. Set the group X/Y/width/height or drag its eight handles to resize together. Undo restores the group edit. Selection stays inside one window. Select full-page backgrounds from Outline; Alt-click selects a canvas.

Gradient controls and prepared pages

Rectangles, circles, meters, sliders, gauges and geometric buttons have a Gradient fill section with start/end colors and direction. A sprite-sheet button uses its image colors; disable its skin to select a geometric gradient. Native C renders these fills without scattered dithering, although the 256-color palette can show bands. They require firmware advertising tdui.SUPPORTS_GRADIENT_FILLS. Try examples/gradient_controls.json.

On current firmware, matching canvas rectangles on different pages share a multi-page canvas. All cached page painters run once before the app's on_ready callback. A page change selects prepared content atomically; images and fonts are loaded once. Dynamic values still draw when updated. This deliberately spends startup time and bounded memory to keep later page changes predictable. Arbitrary user handlers can still add work. Background page warming is not enabled: handlers may rely on controls on every page already existing. For lower-memory boards, keep the design within the editor's smaller resource limits.

Desktop login before kiosk

On boards with accounts, choose a user and enter its existing password before the kiosk starts. CrowPanel's login Keyboard supports touch entry. Root can enable remembered login using its checkbox, the native Users app, or bootuser NAME in /root/.tdshrc.tdsh. A successful password login is required to create the remembered proof. Use bootuser --require-password to clear it. A valid remembered login proceeds directly to the app's configured welcome screen. These device settings are independent of the app's entry-page setting and the isolated App Builder simulator.

Native code inside a TDAPP

Open Export options and choose Compiled app target: Portable bytecode (default), Native ESP32 / ESP32-S3 / CrowPanel, or Native ESP32-C6. Apply options, then Export app or Export .mpy. Native export uses the local helper and matching mpy-cross; it needs root and executable internal RAM on the selected board. The package still includes editable JSON and assets. Keep your source and JSON for recompilation. A wrong CPU or MPY ABI is rejected before package extraction.

This compiles Python into native machine instructions. C-built native .mpy modules may also be imported as assets when compiled with MicroPython's matching dynamic-module toolchain. All native dependencies in an app must target the same CPU. Native code can help calculation-heavy handlers; it does not automatically make C drawing, storage or display DMA faster. The example's native main file is approximately four times its bytecode size, so test memory and timing on hardware before selecting it for deployment. Portable bytecode remains the recommended starting point.

The browser simulator runs generated Python source. An ESP-native dependency needs an explicit portable .py implementation in a helper project directory, or must be tested on the board. See the official native-module guide for C module compilation.

Matching appearance across a selection

Select elements with Shift/Ctrl. Every applicable shared field remains visible; equal values are filled, while differing values are blank or Mixed. Choose Corner style to make rectangular panels, buttons, meters, sliders or gauge backgrounds straight or rounded. Circle and line geometry is unchanged. Gradient fields have independent mixed states: changing the start color preserves each element's end color and direction. Enabling a geometric gradient on an image-skinned button replaces that skin.

Text background offers Transparent and Solid color for generated-font and built-in canvas text. Transparent uses the artwork already behind the text; the font asset itself stores glyph coverage. Select several text elements to apply a common background mode. Set Background to choose the solid palette color.
